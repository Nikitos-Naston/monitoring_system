# Сервис преобразования Modbus через MQTT и Starlark

Сервис принимает нормализованные слова Modbus, находит версию шаблона и
сохраняет отдельный JSON для каждого события. Демонстрационный издатель
берёт исходные данные из массива и отправляет их через настоящий MQTT-брокер.

```text
Тестовый массив → MQTT-издатель → брокер → MQTT-подписчик
                                              ↓
                             (device_id, poll_id) → маршрут и шаблон
                                              ↓
                                 Starlark → decoded/ или rejected/
```

| Файл | Роль |
|---|---|
| service/fixtures.py | 24 тестовых сообщения, 10 привязок опросов и 6 скриптов Starlark |
| service/mqtt_io.py | Публикация, подписка, восстановление соединения и ручное подтверждение |
| service/templates.py | Одинаковый метод resolve() для массивов и настоящего PostgreSQL |
| service/schema.sql | Профили, версии шаблонов и привязки опросов |
| service/core.py | Валидация, выбор шаблона, дедупликация, запись JSON |
| service/star_worker.py | Исполнение одного шаблона в дочернем процессе |

## Запуск через Docker Compose

Команды рассчитаны на Docker Compose V2 и Linux-контейнеры. Выполни их
из каталога, где лежит compose.yaml.

```bash
docker compose up -d --build --wait worker
docker compose exec -T worker python -m service publish-demo
docker compose exec -T worker python -m tests.verify_demo /data --wait 30
docker compose cp worker:/data/decoded ./decoded
```

Проверка ждёт завершения обработки до 30 секунд. Успешная публикация означает PUBACK от брокера,
а запись файла подтверждается отдельно логом подписчика и проверкой каталога.
Каталог /data хранится в Docker volume. Повторная отправка тех же тестовых
событий сохраняет 24 файла и пишет duplicate в логи. Показать логи можно
командой `docker compose logs worker`.

Для отдельной проверки чтения из БД запусти второй Compose-проект.
У него свои broker, DB, идентификатор сессии в своём брокере и выходной volume.

```bash
docker compose -p sibur-db --profile postgres up -d --wait db
docker compose -p sibur-db build worker
docker compose -p sibur-db run --rm --no-deps worker python -m service seed-demo
TEMPLATE_BACKEND=postgres docker compose -p sibur-db up -d --wait worker
docker compose -p sibur-db exec -T worker python -m service publish-demo
docker compose -p sibur-db exec -T worker python -m tests.verify_demo /data --wait 30
docker compose -p sibur-db cp worker:/data/decoded ./decoded_pg
```

`seed-demo` применяет схему и записывает тестовые версии и привязки.
Повторный запуск сохраняет существующие строки. Используй эту команду в
отдельной тестовой базе. В боевой базе примени схему миграцией и загрузи
согласованные привязки.

## Входной контракт

Топик для одного опроса выглядит как `sibur/modbus/si23-demo-a/cc01-env`.
Отправляй сообщения с QoS 1 и retain=false.

```json
{
  "event_id": "demo-01",
  "device_id": "si23-demo-a",
  "poll_id": "cc01-env",
  "observed_at": "2026-11-10T12:00:01Z",
  "registers": {"256": 2350, "257": 4567}
}
```

Адреса — десятичные строки, слова — целые числа 0–65535. В сообщении один
опрос и полный блок из настроенного диапазона. Значения device_id и poll_id
должны совпадать с топиком. Источник назначает стабильный event_id и сохраняет
точные байты сообщения при повторной отправке. Идентификатор уникален в паре
device_id + poll_id. Префиксы Si-23, идентификаторы и данные в демо условные.

Сервис работает на уровне карт регистров. В реальной системе адаптер перед
MQTT-издателем должен собрать фрагменты и извлечь слова из прикладного
payload СИ-23. Для этого потребуются версия протокола, настройки опросов и
контрольная посылка. Заглушка этого адаптера — функция get_modbus_data().

## Выбор шаблона

(device_id, poll_id) → asset_id + профиль + начальный адрес + размер блока
+ порядок слов → активная версия Starlark.

Например, для cc01-env и cc14-env один шаблон cc_environment читает
смещения 0 и 1. Абсолютный старт у CC01 равен 0x0100, у CC14 — 0x01D0.
Core вычитает начальный адрес маршрута. При опросе CC01 слова 256 и 257
передаются в шаблон как r[0] и r[1].

| Профиль | Какие поля получаем |
|---|---|
| cc_environment | Температура и влажность шкафа управления |
| cc_flags | Дверь, протечка, байпас ИБП, низкий заряд ИБП |
| rc_full | Температура, пыль, дверь, протечка, дым и вентилятор |
| pc_full | Температура, влажность, мощность и энергия по трём фазам, дверь и вентилятор |
| room_environment | Четыре температуры, пыль, гигрометр и давление |
| room_flags | Протечка, статус шкафа, движение, кондиционеры и осушители |

Адреса, размеры слов, единицы и флаги взяты из предоставленной карты
«Modbus RTU edge». Разбиение CC и ROOM на отдельные опросы, привязки и
порядок слов в тестовом наборе заданы для демонстрации. Например, PC02
использует младшее слово первым, чтобы проверить обе ветки.

Контракт скрипта: `transform(r, order)` возвращает словарь с числовыми
или булевыми показаниями. `r` индексируется смещениями от старта, `order`
принимает high_first или low_first. В прежнем HTML-редакторе экспорт был
`transform(reg)` с абсолютными адресами. Для использования такого файла
здесь адаптируй сигнатуру и адреса либо создай шаблон по одному из примеров
fixtures.py.

Каждая версия — отдельная строка. Для публикации вставь новую версию и
переключи active в одной транзакции. При одновременной публикации для одного
профиля сначала заблокируй строку этого профиля в profiles с FOR UPDATE.
Частичный уникальный индекс допускает не более одной активной версии.
Обработчик читает маршрут и версию одним параметризованным запросом.
В выходной JSON записываются профиль и номер фактически исполненной версии.
Сохраняй опубликованные версии для аудита.

## Доставка и выход

После записи и синхронизации файла подписчик отправляет PUBACK. Пишет
во временный файл на том же файловом разделе и публикует итоговое имя
атомарно. Имя — SHA-256 от device_id/poll_id/event_id. Точное повторение
байтов считается дубликатом. Те же идентификаторы с изменившимся телом
записываются в rejected/ и не заменяют результат. Содержимое MQTT
сохраняется в rejected/ в Base64 с ограничением размера.

Ошибка данных, неизвестный маршрут, ошибочный скрипт или превышение
времени его исполнения попадают в rejected/. Ошибка доступа к БД,
файловой системе или сбой процесса Starlark оставляют сообщение без
подтверждения. В этом случае потребитель завершается с ошибкой, а Compose
перезапускает его. Стабильный идентификатор потребителя и сохранённая
сессия брокера позволяют повторно доставить неподтверждённое сообщение.
Выделенный брокер стенда сохраняет сессии в Docker volume. Гарантия
доставки зависит от доступности хранилища брокера, его очередей, политики
сессий и периода между сохранениями. Схема предусматривает at-least-once
с защитой от повторной записи. Сохраняй выходной каталог на постоянном
томе, иначе при его потере потеряется и состояние дедупликации.

## Настройки для подключения к инфраструктуре

| Переменная | Назначение |
|---|---|
| MQTT_HOST, MQTT_PORT | Адрес брокера, по умолчанию localhost:1883 или :8883 при TLS |
| MQTT_USERNAME, MQTT_PASSWORD | Учётная запись MQTT |
| MQTT_TLS=1, MQTT_CA_FILE | TLS с проверкой сертификата; свой CA необязателен |
| MQTT_CLIENT_ID | Стабильный ID подписчика для возобновления сессии |
| TEMPLATE_BACKEND | fixture или postgres |
| DATABASE_URL | DSN PostgreSQL для режима postgres |
| OUTPUT_DIR | Каталог для decoded/ и rejected/ |
| STARLARK_TIMEOUT | Тайм-аут дочернего процесса в секундах, по умолчанию 3 |
| READY_FILE | Файл готовности после подтверждения подписки брокером |

Локальный compose использует демонстрационные учётные данные и анонимный
брокер без порта на хосте. При внедрении подключи защищённые MQTT и
PostgreSQL, передавай секреты через инфраструктуру, ограничь MQTT ACL по
устройствам, выдай worker только SELECT на таблицы и используй постоянный
Linux-том с поддержкой hard links и fsync. Для доступа к PostgreSQL через
недоверенную сеть используй проверку сертификата сервера (sslmode=verify-full).
Шаблоны публикует доверенный администратор. Тайм-аут ограничивает длительность
запуска скрипта; контейнер дополнительно ограничен по памяти и числу процессов.

На одном наборе топиков запускай одного подписчика с указанным стабильным
ID. Обработка последовательная, на сообщение приходится один дочерний
процесс и в режиме postgres одно подключение. Пропускная способность
на реальной нагрузке и работа с реальным оборудованием требуют отдельной
проверки. Контролируй свободное место, рост очереди брокера, ошибки worker
и появление записей в rejected/.
